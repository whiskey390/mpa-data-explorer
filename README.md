# MPA Data Explorer

Pick a marine protected area, see the OBIS records inside it, and read who published them and when.

**Run it** (needs Docker and internet access; no account, no key):

```
docker build -t mpa-data-explorer .
docker run --rm -p 8000:8000 mpa-data-explorer
```
Open http://localhost:8000. Tests: `pip install -r requirements.txt pytest && pytest`.

## What was built
- Demo country: **Portugal** (real data; the fictional Costa Verde has none). Areas: marine Natura 2000 sites, EEA service, CC BY 4.0.
- Records: OBIS API v3, fetched live per area and cached for an hour, then tested against the exact boundary.
- Panel: records per year (empty years in orange), per phylum or class, per OBIS node, per publishing institution, and the share from the national node.
- Same table feeds map, panel and CSV. Four free base maps. One Python file (`app/main.py`), one HTML file, Leaflet vendored.
- Data sources and licences: `docs/DATA_SOURCES.md`.

## Deliberately not built
- No database, login or user accounts: not needed to answer the questions.
- No server-side clustering or vector tiles: canvas markers cope with the cap below.
- No WDPA: its terms forbid redistribution and need a token.

## Known limitations
- Each area keeps at most 20,000 records (`MAX_RECORDS`). Above that the panel says so and counts describe a subset, the first records OBIS returns, not a random sample.
- "Institution" is the `institutionCode` of each record, often blank or inconsistent. The national node is matched by name (`NATIONAL_NODE=portugal`).
- The boundary is simplified to about 50 m for display and testing.
- Large areas take a while on first load.
- Live calls to OBIS and the EEA service were not possible from my build sandbox. Response shapes were read from live pages; the code is tested against mocked replies. The marine-site filter (`is_marine='True'`) was read from the service's own value list; the full list query was rate-limited. Docker could not pull its base image there either, so the image was not built. Please report any failure.

## Docker choices
- **Base image:** `python:3.12-slim`. Debian-based, so every dependency installs from a prebuilt wheel with no compiler. Alpine (musl) would be smaller but needs source builds for numpy and shapely. In production I would pin the image by digest and rebuild weekly.
- **Pinning:** `requirements.in` lists four direct packages; `requirements.txt` is generated by pip-compile with hashes, and installed with `--require-hashes --only-binary`.
- **Trade-offs accepted:** single stage, because nothing is compiled. Image is roughly 250 MB (shapely brings numpy). Dependencies sit above the code so rebuilds after code edits take seconds. Leaflet is committed to the repo, so the build needs no Node.
- **Configuration and secrets:** all settings are environment variables (`MPA_QUERY_URL`, `MPA_WHERE`, `COUNTRY_LABEL`, `NATIONAL_NODE`, `MAX_RECORDS`, `CACHE_TTL_SECONDS`, `OBIS_API`). None is secret today. A future key (say a WDPA token) would come from the orchestrator's secret store, as an env var or mounted file, never in the image or the repo.
